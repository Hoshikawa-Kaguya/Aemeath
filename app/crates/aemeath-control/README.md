# aemeath-control

主程序的控制面：`usbip.exe` 命令行封装、与引擎的 IPC、电平读取、槽位的挂载维护与首次注册。

## 模块

| 模块 | 内容 |
|---|---|
| `usbip_cli` | 只用 5 种调用：`--version`、`port`、`attach --once`、`attach --stop`、`detach -p`。只按退出码判断成败；调用不弹控制台窗口，10 s 超时 |
| `engine_client` | 握手、心跳（1 s 一次，3 s 收不到任何消息判为假死）、断线重连（500 ms）。调用方只提交"当前想要的拓扑"，断线期间提交多次时重连后只下发最后一份；修订号由客户端分配，跨连接也递增 |
| `meters` | 读取引擎写在共享内存里的节点电平。读取时取走峰值，读得慢也不会漏掉 |
| `slots` | 挂载维护与首次注册，见下 |

## 挂载维护

被占用的槽位，三者同时满足才算正常：

1. 已导入列表里只有一个指向 Aemeath 服务端口和该 busid 的条目；
2. 服务端报告连接有效；
3. 端点处于 ACTIVE 状态。连上后有一段宽限期（90 s，首次安装驱动可能接近 1 分钟）。

没有被占用的槽位保持卸下。只碰指向 Aemeath 服务端口的条目。

- **检查时机**：每 5 s 一次；占用状态改变、引擎连上（等 500 ms，让引擎补发的槽位连接快照先到）、端点有变化、服务端报告占用中的槽位断开时立即检查。系统从睡眠唤醒后由主程序调用 `check_now`。
- **检查分两遍**：
  - 不需要端点信息就能判定的情况（拔出、未导入、重复导入、服务端没有连接）先处理；
  - 再查询端点（2 s 超时）。设备正在增减时，Windows 会把端点查询阻塞好几秒（实测引擎被结束后约 5 s），不能让修复等它。
- **修复**：
  1. `attach --stop` 只停这一台的后台重试；
  2. 卸下残留和重复条目；
  3. 用 `attach --once` 挂载；
  4. 以服务端报告收到 import 为成功判据；
  5. 失败后按 1、2、4、8、10 s 退避，连续 3 次失败标记为 `Failing`，由界面提示用户。
- **格式**：每次连接后端点首次变为 ACTIVE 时，如果设备格式的采样率与引擎不同，就改成引擎采样率，样本格式不变。端点上已有的流会被作废，但这时槽位刚出现，还没有应用在用。
- **线程**：COM 对象由专用线程持有（MTA），其余都在主程序的 tokio 运行时上。

## 首次注册

1. 下发 `registration_topology`（16 个虚拟节点，没有连线），让服务端导出全部槽位；
2. 把全部槽位设为被占用；
3. 用 `RegistrationProgress` 跟踪：挂载正常且采样率为引擎采样率才算完成；
4. 换回正式的拓扑和占用集合，挂载维护会卸下没有被占用的槽位。

是否已完成由主程序记录在配置里。

## 测试

- 单元测试：
  - 命令行输出的解析，用 `testdata/usbip-cli/<版本>/` 里从真实的 `usbip.exe` 录下的输出。这些样本保留 CRLF 原始字节，`.gitattributes` 里设为 `-text`；
  - 挂载判定、注册进度、端点匹配。
- 集成测试 `tests/engine_client.rs`：对照一个假的引擎服务端，覆盖握手、下发、断线重连、心跳超时、协议版本不符、退出。
- 在本机实际运行的示例（开发身份）：
  - `usbip-status`：打印 usbip-win2 版本和已挂载设备；
  - `slot-maintenance`：拉起 `aemeath-host` 子进程，依次验证注册、按占用拔出、引擎崩溃恢复、清理，约 25 s。

    ```text
    cargo build --release -p aemeath-host
    cargo run -p aemeath-control --example slot-maintenance -- <aemeath-host.exe> <数据目录>
    ```
